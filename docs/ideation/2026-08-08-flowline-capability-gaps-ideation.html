Context

Grounding Context

Codebase Context

Flowline v1.0 (released 2026-08-01) wraps PAC CLI into a Git-based clone → push → sync → deploy loop for unmanaged solutions, with PROD as source of truth and DEV as a branch of PROD via pac admin copy.

Ten commands ship today: init, clone, push, sync, deploy, provision, generate, status, drift, sln add. Attribute-driven plugin and Custom API registration, web-resource sync with form-event auto-wiring, DTAP gates, orphan cleanup, typed exit codes and observability waves 1–1.5 are all already in place.

This maturity is why the search had to go past the obvious: most of the surface-level gaps a generic scan would name are already closed.

Documented costs of the model

docs/ALM-strategy.md §9 names four costs the unmanaged / PROD-as-truth model accepts:

  • Deletion does not propagate — imports are additive
  • No solution-level rollback — imports are destructive
  • Merge-behavior components (forms, sitemap, ribbon, app modules) merge rather than replace
  • Drift discipline required — no managed-layer audit trail

Three of the seven survivors below attack one of these directly. That is deliberate: these are the costs the product signed up for, and the ones where tooling — not a model change — is the available lever.

Prior exploration (14 documents, May–July 2026)

Seven themes recur across two or more prior ideation docs: Solution Checker integration, multi-solution support, configuration management, DTAP enforcement, observability, CI/CD integration, and artifact integrity.

Overlap with a prior doc did not disqualify an idea — most were never built, so they remain "not yet in Flowline." But each surviving idea states which prior doc it touches and what this run adds. Ideas that only re-treaded were cut.

External context

ALM Accelerator is deprecated — Microsoft Learn states no new features are being added and issues are no longer reviewed. Its replacement, Power Platform Pipelines, has no source-code integration and no code-first development.

Native Dataverse Git integration (GA) cannot rebuild a solution from repo sources, has no merge/compare/conflict resolution, binds solution to branch immutably, and is Azure DevOps only.

The mid-tier is vacated. The questions Flowline is structurally positioned to answer — "what will this deploy change, and has the target drifted?" — are the exact ones the sanctioned tools cannot.

The YAML question, settled YAML is not available through clone or sync — which is the entire path Flowline's loop runs on, so the format is out of reach whatever pack can auto-detect. This confirms the internal 2026-05-19 conclusion rather than overturning it, and it resolves a genuine documentation conflict: Microsoft Learn's source-control page describes pac solution pack/unpack supporting YAML by auto-detection from 2.4.1, while a separate Learn FAQ states clone, unpack and sync do not. Local inspection of pac 2.9.3 found no format flag on pack, unpack or clone, which was consistent with either reading. The consequence follows from two facts rather than from one claim: Microsoft's own format comparison records that the XML source format carries no canvas app (.msapp) and no modern flow representation, and YAML — the format that does — is unreachable through the commands Flowline uses. So canvas apps and modern cloud flows stay outside what a Flowline repo can hold, and that reads as a boundary of the approach rather than a backlog item.

1. Top pick
Preflight the import against the target's own metadata
IMPLEMENTED TOP PICK Axis 1 · Deploy & promotion Confidence 85% Complexity Low
Implemented — 2026-08-09

Shipped as the missing-component gate on deploy, behind --skip-component-check. Merged to master at 073dca1. Plan: docs/plans/2026-08-09-001-feat-deploy-import-preflight-plan.md.

One thing below is wrong. The card treats the class the maker portal already lists as out of scope. That exclusion was dropped during scoping: the portal's remediation page and its Install buttons never appear on a CLI deploy, so a first-party dependency costs a Flowline user exactly what any other missing component costs. The gate blocks on everything and names the owning solution, which is what tells you whether to install it in the target or drop the dependency in DEV.

Two claims were confirmed by measurement, one was not. Verified live: the message does filter against the target rather than echo the solution file back, and identity comes back as names rather than GUIDs. Not confirmed: "runs in seconds" holds for ordinary solutions (~6s at 0.5 MB) but cost tracks payload size — 32 MB costs ~112s and 64 MB ~217s, with no rejection observed at any size. See docs/solutions/tooling-decisions/retrieve-missing-components-payload-cost.md.

Description
Before deploy imports anything, hand the packed solution's required-component list to Dataverse's own RetrieveMissingComponents message against the target and fail fast with a named list of what the target lacks. The response carries both the dependent component and the required solution name, so the error becomes actionable rather than diagnostic: "account.new_region is required by form Account Main but absent in prod." Runs in seconds against a live connection, writes nothing.
Basis
external: Microsoft's RetrieveMissingComponentsRequest is documented as taking the solution file's required-component list, querying the target organization, and returning what is absent — verified independently by two agents this run against Microsoft Learn. direct: a grep of src/ for RetrieveMissingComponents, MissingComponent and RetrieveDependenciesForDelete returns nothing — Flowline never asks. Missing-dependency failures on import are one of the two most consistently reported Dataverse ALM frustrations in independent community sources.
Rationale
Every guard Flowline ships today validates Flowline's own preconditions — drift, DTAP order, solution type, dirty working tree. None validates the payload against the target's actual metadata. That asymmetry means the failures users actually hit are discovered mid-import, in the worst possible position: a partially applied unmanaged import against an environment with no solution-level rollback. This is the highest ratio of pain removed to code written in the whole set, and the mechanism is one SDK call.
Not already present
deploy --dry-run skips the import but validates only Flowline's own gates. --skip-solution-check relates to Solution Checker, which is static analysis of the source and knows nothing about the target org's inventory. drift compares committed source against a target for changes — a component can be entirely drift-free and still fail to import for a dependency it never touched.
Prior art overlap
The 2026-07-03 pipeline-dashboard doc proposed a "pre-flight manifest gate" and the 2026-06-07 deploy doc proposed "config drift pre-flight" — both about presenting Flowline's own gate verdicts more legibly. Neither contemplated asking the target what it is missing. That is the addition.
Downsides
Diagnosis only — unlike a package manager, Flowline cannot then install the missing first-party dependency for you. Adds a round trip to every deploy, so it likely wants to be skippable. And it does not catch data-dependent import failures, only metadata ones.
2
One per-target state manifest — connection references, environment variables, and workflow state
Axis 1 · Deploy & promotion Confidence 90% Complexity Medium
Description
Three separately-tracked gaps reduce to one shape: "declare what target-specific state should be true after import." Connection references and environment variables have no Flowline binding at all. Classic workflows and business process flows silently reset to Draft on every import. Flow ownership assignment was proposed and never built. Rather than three flags with three schemas, define one per-target manifest that deploy reads automatically, and populate it by auto-discovery from the packed solution rather than by hand-authoring.
Basis
direct: docs/ALM-strategy.md:696-699 — "Deployment settings file — not implemented. No --settings-file or create-settings usage exists in src/." direct: STRATEGY.md:114 — "Restore state of workflows on deploy (--no-restore flag) — post-v1." direct: a deploy-state brainstorm records the consequence plainly: automations that were active stop running with no warning and no error, and teams find out when a business process fails. external: connection references failing to update via deployment-settings files is an open issue against Microsoft's own build tools, so the naive "just call the PAC settings file" path has known sharp edges.
Rationale
This is the one gap that blocks unattended CI/CD outright for any solution using flows or connectors — every other deploy feature already assumes an environment-agnostic artifact, and this is the assumption that breaks. It also converts a silent production-breakage class (automations quietly stopping) into something the tool handles by default rather than behind an opt-in flag. Worth checking before designing: pac solution create-settings already exists in the installed PAC 2.9.3 — "Create a settings file from solution zip or solution folder." The generation primitive is on disk and unwrapped, which makes this materially cheaper than it looks.
Not already present
No --settings-file flag exists anywhere in the command surface, and nothing auto-discovers required references from a packed solution. IPostDeployService ships, but it is a DI hook a developer implements in C# — not a declarative file a non-developer can edit per environment. That distinction is the whole point.
Prior art overlap
The most re-treaded ground in the corpus: the 2026-07-01 post-deploy doc proposed workflow-state snapshots and secure config injection; the 2026-07-02 ALM Accelerator doc ranked per-env deployment settings files in its top seven. Both assumed hand-authored files and separate mechanisms. What this run adds is the consolidation — one schema, one read path, auto-derived — plus the observation that it is a recurring top-ranked idea that has now gone unbuilt across three documents, which is itself worth asking about.
Downsides
Secrets. A manifest committed to git that carries connection values has a real security surface, so the schema needs an explicit split between what is declarative and what stays a code hook or an environment-variable lookup. Combining three concerns into one file also risks a schema that serves none of them cleanly.
3
Disposable DEV: import to create, tear down when done
Axis 3 · Environment lifecycle Confidence 75% Complexity High
Description
Make a DEV environment as cheap to create and discard as a Git branch, so the unit of work is branch → environment → change → deploy → delete rather than one long-lived DEV that every change shares. (1) Create by import — the load-bearing move, and the one already written down as a TODO in the code: provision an empty environment and import the solution into it, instead of copying the whole environment. Minutes instead of hours, and it works against a Developer environment, which pac admin copy cannot target. (Complexity is rated High for the full bundle below; this first move alone is medium.) (2) Let the branch say which DEV — the four fixed URL properties allow exactly one environment per role, so "a DEV per branch" has nowhere to live. The fix is not a registry inside .flowline: git already tracks which branch you are on, and provision already derives both the environment name and its URL from a --suffix. Default that suffix to the current branch and the mapping needs no storage at all — feature/ABC-123 resolves to the same environment every time, on every machine, with nothing written down and nothing to merge. (3) Tear down — provision's missing inverse: delete the environment when the branch merges, with the same mechanism serving reset. A lease that expires is the unattended version of the same thing, and is the softest, most deferrable part of the idea.
Basis
direct: ProvisionCommand.cs:194-195 carries the strategy as a verbatim TODO: "add a different strategy where we import solution(s) from prod, instead of copying the whole environment. should be much faster. also for reset the environment. ⇒ use this path also for Development environments." direct: the cost of the current mechanism is in the same file — ProvisionCommand.cs:178 passes --max-async-wait-time 480, an eight-hour cap, and :166 concedes that Ctrl-C only "stops pac's poll — the copy is a server-side operation and keeps running regardless." direct: ProvisionCommand.cs:134 has reset as a dead comment linking Microsoft's reset-environment doc, with no implementation. verified against pac: pac admin copy cannot target a Developer environment, which is why every provisioned DEV today is a Sandbox; pac solution clone and pac solution sync both work fine against a Developer env, so nothing but the copy mechanism forces that. direct: ProjectConfig.cs:16-19 holds ProdUrl, UatUrl, TestUrl, DevUrl as four fixed properties, and FlowlineCommand.cs:20 defines a closed enum EnvironmentRole { Prod, Uat, Test, Dev } — so "DEV" is a single slot, and two concurrent branches cannot both have one. direct: the derivation this idea needs is already implemented, just not driven by the branch: ProvisionCommand.cs:55-60 builds targetDisplayName as "<Prod> <suffix>" and targetUrl as https://<organization>-<suffix>.<host>/ from an existing --suffix setting, and :100 passes --domain <organization>-<suffix> to pac admin create — so the URL is set by Flowline, not guessed, and a suffix determines an environment exactly. direct: GitUtils.GetCurrentBranchAsync already exists and is already used elsewhere in the codebase. direct: FlowlineCommand.cs:168 is the single seam every command resolves through — var url = GetOrUpdateUrl(role, inputUrl, settings) — so branch-derived resolution is one function, not a schema. direct: and the reason it must not be a committed value: SyncCommand.cs:57 and ProvisionCommand.cs:189 both call Config.Save() during normal work, so .flowline is a live mutating tracked file — a per-branch DevUrl committed into it would be rewritten mid-workflow, prompt "Overwrite it?" on every branch switch (ProjectConfig.cs:60-68), and carry the dead environment's URL into master on merge. A convention doc dated 2026-06-06 records the other half of the same cost: adding a named environment means editing six files, and omitting one leaves that command silently broken for the new role. external (Microsoft Learn): Developer environments are capped at three per maker, carry 2 GB of database and 750 flow runs per month, cannot host Dynamics 365 first-party apps, and — the part that bounds the licensing argument in both directions — do not count against the tenant's capacity quota. external (Microsoft Learn): Microsoft already runs the lease idea on exactly these environments: a Developer env unused for 30 days is disabled, and one unused for 90 days is removed from the tenant if the owner does not respond. external: DHCP leases — a finite pool with clients that acquire unilaterally and vanish without releasing is solved by expiry-by-default, not by better bookkeeping.
Rationale
The shape being copied is GitHub flow. A branch is cheap because creating and deleting one costs nothing, which is what makes "one branch per change" a habit rather than a ceremony. A Dataverse DEV is the opposite: a whole-environment copy measured in tens of minutes against an eight-hour cap, so teams keep one long-lived DEV and every feature, fix and hotfix shares it — which is exactly the situation Flowline's PROD-as-master model is otherwise built to avoid. Import-based provisioning is what changes the economics, and it is the move here: a solution import is minutes, and it can target a Developer environment, whose capacity does not count against the tenant's quota at all — so for a small team the cheap unit becomes a Developer env per developer rather than a Sandbox drawn from shared storage. Per branch is the aspiration, not the entitlement: a maker gets three Developer environments, so beyond that the Sandbox path is still what serves concurrent branches, and the Developer route only fits solutions with no Dynamics 365 first-party dependency.

The second move is what lets that loop run more than once at a time, and the cheapest version of it stores nothing. The mapping "which DEV belongs to this work" is not new information Flowline has to keep — it is the branch name, which git already tracks, in the one place that is always correct and never merged. Since provision already turns a suffix into both a display name and a domain, defaulting that suffix to the sanitized branch makes the environment's identity a pure function of where you are standing: feature/ABC-123 resolves to <org>-abc-123 on every machine, with no lookup, no registry entry, no schema version, and nothing to migrate. It also lands as an override at one seam rather than a new data model, so a single-DEV project that never branches sees no change at all. A stored registry would be re-implementing git branch in JSON, inside the file that gets merged between branches — which is precisely where the mapping must not live. Teardown closes the loop and is the smaller half of the same mechanism — a hotfix environment nobody deletes is the long-lived DEV coming back through the side door. Automatic reclaim by lease is the unattended version of teardown and the most deferrable part of the whole idea: for a small team, an explicit teardown covers it, and expiry is worth building only once environments outnumber the people tracking them.

Not already present
provision --copy {full,metadata} selects between two pac admin copy breadths — both are whole-environment copies, neither is a mechanism change, and neither unlocks a Developer target. --allow-overwrite overwrites an environment you are already reusing; it neither creates nor releases one. There is no teardown, delete, or reset command in the surface at all. --suffix exists on provision but defaults to the role name (Dev/UAT/Test), never to the branch, and nothing downstream reads it back — push, sync and generate resolve DEV from .flowline or a --dev flag with no branch awareness anywhere in the chain. status shows URLs, login state and versions, but not environment type, provisioning state, age, or ownership.
Prior art overlap
None. Provisioning strategy and teardown appear in no ideation doc at all; the TODO at ProvisionCommand.cs:194 is the only record either has. Environment representation appears in the corpus only as a documented workaround — the 2026-06-06 convention doc explains how to survive the six-file edit, never proposes removing it.
Downsides
Data seeding is the open question on import-based provisioning, and it is the one that decides whether the loop is usable: a copy carries the data, an import does not, so a freshly imported DEV starts empty and deciding what a DEV actually needs — nothing, a seed script, a subset — is a product conversation, not an implementation detail. It also only carries what the solution carries, so anything living outside it (environment variable values, connections, security-role assignments) has to be re-established per environment — which is the same set idea 2's per-target manifest exists to hold, so the two ideas meet here. The Developer-environment target has its own ceiling worth stating before anyone plans around it: external (Microsoft Learn) — three per maker, 2 GB of database, and no Dynamics 365 first-party apps, which rules the route out entirely for a solution that depends on them. Branch-derived resolution has two open ends of its own. Collisions: two people on the same branch name in the same tenant derive the same environment, so the scheme needs a discriminator or an explicit escape hatch — git config branch.<name>.flowlineDevUrl is the idiomatic one, since git already owns the branch.<name>.* namespace for remote and merge and it is never committed. Name shape: branch names are richer than domain names, so feature/ABC-123 needs sanitizing, and the result must stay stable under sanitization or the environment becomes unreachable from the branch that owns it. Long or unlucky branch names will collide after truncation; that rule needs deciding once rather than per command. Note also that provision currently persists the URL it derives (ProvisionCommand.cs:70 then :189) — for a per-branch DEV that write becomes wrong, not just redundant. The related idea of making provision non-blocking belongs here too, but adds cross-invocation operation state, which the codebase currently has none of.
4
Let git carry deletions — and stamp what each target has applied
Axis 5 · Team, CI & comprehension Confidence 75% Complexity Medium
Refined — 2026-08-14

The tombstone artifact is gone, and so is the framing that led to it. Tombstones exist in Cassandra, Dynamo and CRDTs because those are additive stores with no history — absence is the only signal, so deletion has to be written as a positive record. Git is not that store. A file present at the target's stamped commit and absent at HEAD is already a positive, authored, timestamped, reviewed deletion record. The tombstone role is filled.

What Flowline lacks is not the record but the pointer: where each target sits in that history. Without it there is no way to ask "which deletions has PROD not applied." The card below is now written pointer-first, in two tiers of authority. The structured-output half — --json on sync and drift — survives on its own merits and is stated separately, because it is a different feature with a different justification.

Description
The deletion record needs no new artifact. git diff --name-status <stamped-ref>..HEAD -- Solution/src/ returns the deletions; the D lines are the tombstones, keyed by the GUID-bearing path rather than by a display name, and SolutionChangeSummary.ParseComponentPath already maps that path to a component group and key. Nothing is persisted, no schema is published, no expiry heuristic is needed.

The gap is the ref, and it comes in two tiers that differ in authority, not in mechanism:

Report tier — assembled from parts that already exist. A target's installed solution version is already readable (PacUtils.GetSolutionVersionAsync, used today by status), and sync already ends by telling the user Commit, then 'git tag <version>', with ToTagVersion defining the tag shape. So the version installed in a target already resolves to a commit through a convention Flowline itself prints. That is enough to report, and it is where the natural command extension lands: drift today answers "what does this target have that source does not" purely by inference — give it the git range as a second input and it answers the declared half too, in the same command.

Authorization tier — a genuinely new write. A user-placed, unverified tag cannot authorise destruction; that is the same inference-versus-declaration line this doc draws about components, applied to the pointer. For idea 6 to delete, deploy must record the exact tree it shipped, into the target. Deploy already computes that SHA (DeployCommand.cs:144) and throws it at a local artifact-cache manifest. Writing it into the target is the missing piece — and the codebase has no precedent for writing any such marker, so this is real work, not a free consequence.

Basis
direct: CHANGES.md is a lossy rendering, and the losses are the identity: WriteChangesFileAsync (SolutionChangeSummary.cs:219) writes ComponentName only — FilePaths never reaches the file — and ComponentName comes from ResolveXmlNameAsync, a localized form or view title, not a key. It is also overwritten each sync (SyncCommand.cs:162), so recovering deletions from it means parsing generated prose out of per-commit blobs. The git history of Solution/src/ is the non-lossy version of the same record. direct: the path→component mapper already exists — ParseComponentPath (SolutionChangeSummary.cs:268) resolves a Solution/src/ path to a group and component key, which is exactly what the range query needs; note it consumes a path, so it works on a committed-range diff even though its current caller ComputeAsync uses git status (working tree versus HEAD). direct: the version pointer already exists at both ends: PacUtils.GetSolutionVersionAsync:448 reads a target's installed version via pac solution online-version and StatusCommand.cs:155 already calls it per environment; SyncCommand.cs:111 sets the version in DEV and SyncCommand.cs:168 ends every sync with Synced <v>. Commit, then 'git tag <v>' when ready to deploy., with ToTagVersion:199 defining the join shape as the first three parts of the four-part version. direct: deploy already computes the SHA of what it packed — DeployCommand.cs:144 GetLastCommitShaForPathAsync — and writes it to a local artifact-cache manifest (:245, ArtifactCacheEntry:507), never to the target. direct: nothing writes any marker into a target: a verifier found EnvironmentVariableDefinition and EnvironmentVariableValue only as component-type catalog entries (ComponentTypeCatalog.cs:380-381), no writes of solution description or publisher anywhere, and PostDeployContext (IPostDeployService.cs:24-32) carries Service, Solution, Mode, PackagePath, DataverseSolutionSrcRoot and DeleteOrphansConsent — no commit SHA. direct: git tags appear in src/ exactly once, as the instruction string at SyncCommand.cs:168; nothing creates, reads or verifies a tag. direct: sub-component deletion is already modelled and already diffed against a git blob — DiffEntityAttributes emits new SubChange(name, ChangeStatus.Deleted), and GetHeadXmlAsync runs git show HEAD:<path> to get the prior version. direct: DriftCommand.cs:48 calls orphanCleanupService.CompareAsync(...) and uses the result for console rendering and exit-code selection only. external: the tombstone precedent this idea previously leaned on (Cassandra, Dynamo, CRDTs) argues the opposite way once read carefully: those systems replicate deletion as a positive record because they have no history. Git does, which is why the record needs no invention and the pointer does.
Rationale
The deletion record was never the hard part, and building one would have been building a second copy of git. Every property a tombstone is supposed to supply — a positive statement that something was removed, an author, a timestamp, review, an ordering — a commit already supplies, in a store the team already trusts and already reviews. Inventing an artifact alongside it buys a schema, a compatibility commitment, an expiry rule and a merge-conflict surface, in exchange for information that was already there.

Splitting the pointer into two tiers is what keeps this honest. The costs are asymmetric: a wrong range in a report produces a wrong report, which a human corrects; a wrong range feeding a deleter produces a silently missed deletion — PROD keeps a component the team believes is gone — or a deletion no one declared. So the version-plus-tag route, cheap and already half-built, earns the reporting job and nothing more, while the deleting job waits for a stamp written by the operation that performed the import. That split is the same inference-versus-declaration line this doc draws about components, applied one level up to the pointer itself.

It also lands the read in a command that already exists for the question. drift's entire job is "what does this target have that source does not," answered today by inference alone. Giving it the git range adds the declared half without inventing a command, and makes the two answers directly comparable in one place.

Structured output — the separable half
Idea 4 originally bundled two things. Persisting the change model as --json on sync and drift survives, but on its own justification: CI consumption, release notes, and a machine-readable deploy receipt. It is an output-format feature. It is not the deletion mechanism and should not be planned as a prerequisite for one — the deletion range is answered by git whether or not the JSON ever ships.
Not already present
No --json or structured output on sync or drift; the model is rendered and dropped. No --since or range input on drift — CompareAsync takes source and target, never a git ref. No marker of any kind is written into a target environment on deploy, and nothing reads a target's installed solution version except status. No code creates, reads or verifies a git tag; sync prints the command and stops there. CHANGES.md is generated (not, as first assessed, a static file a human maintains) — but it is overwritten each sync, drops the file paths that carry component identity, and is never read back.
Prior art overlap
The 2026-07-03 pipeline-dashboard doc proposed a "deploy receipt JSON" and the dashboard doc a versioned --json schema — both scoped to deploy and framed as output formatting; those land on the separable half above. The 2026-06-07 deploy doc proposed --prune, refining inference rather than replacing it. What this adds is that the deletion record already exists in git and the missing piece is a per-target pointer into it — and that half of that pointer is already printed to the user at the end of every sync.
Downsides
The tag is placed by a human, at their discretion, and nothing verifies it. Tag at commit 10, deploy at commit 15, and tag..HEAD excludes 11–15 — the range is a subset, and deletions in that window vanish from the answer. A false negative in a deletion-propagation mechanism is precisely the failure idea 6 exists to remove, so this is the reason the tag route is capped at reporting. The cheap way to raise its trust without a Dataverse write is for deploy to verify at ship time that HEAD carries the tag matching Solution.xml's version, and refuse or warn otherwise.

The join key is many-to-one in two independent ways, and neither is a discipline failure. ToTagVersion:199 keeps three of four parts, so 1.2.3.0 and 1.2.3.1 resolve to the same tag. And sync --bump none (SyncCommand.cs:100, :108) reuses the current version across any number of syncs and commits, so one version can name an arbitrarily long run of history. Both collapse distinct commits onto one ref, and both fail in the subset direction — the same false negative as a mis-placed tag, arrived at mechanically.

One link is inferred rather than verified: that the target's installed solution version ends up equal to the packed version. The code path is at least unambiguous — ImportSolutionAsync (DeployCommand.cs:690) has a single branch, pac solution import --path <zip>, and nothing in deploy reads or writes a version around it, so the version can only come from the zip. What remains unconfirmed is the Dataverse-side behaviour on the unmanaged-into-existing-PROD path that is Flowline's default model. If it does not hold there, the report tier has no join key at all. Confirm before planning on it.

The authoritative stamp has no existing write path — solution description, an environment-variable value, or a purpose-built table are all new work with different costs, and the last one puts a Flowline table inside the customer's solution. PostDeployContext would also need to carry the SHA.

Mechanical limits: a stamped SHA absent from the local object store breaks the range — force-push is the exotic case, CI shallow clone (fetch-depth: 1) is the common one, and both want the same git cat-file -e <sha>^{commit} guard falling back to report-only. Sub-component deletions (an attribute dropped from Entity.xml, an option from an optionset) arrive as M, not D, so they need git show <ref>:<path> plus the existing Diff* functions, and GetHeadXmlAsync hardcodes HEAD: today. Reuse also crosses a project boundary: ParseComponentPath is internal to the Flowline CLI project while the consumer sits in Flowline.Core, and Core must never reference Flowline — AGENTS.md already lists SolutionChangeSummary among the known-misfiled files, so this is pre-existing debt to pay, not new debt.

Scope stays bounded to Solution/src/. One flag on the earlier version of this card: it asserted plugin types and steps never appear in solution XML, but ParseComponentPath:347 handles an SdkMessageProcessingSteps/ folder. Check that against a real synced project before planning around either claim.

5
push --watch for the inner loop
PLANNED Axis 2 · DEV inner loop Confidence 70% Complexity Medium
Planned — 2026-08-08

Plan written, not yet implemented: docs/plans/2026-08-08-001-feat-push-watch-mode-plan.md (implementation-ready). Scope is watch mode for push only — one-shot push, sync, and deploy semantics unchanged, and Flowline does not take over building.

Description
The web-resource loop today is npm run build → flowline push → repeat, by hand, all day. A watch mode holds one authenticated session, watches the build output, content-hashes each candidate, pushes only what changed, and debounces the publish.
Basis
direct: a repo-wide search finds no --watch flag and no FileSystemWatcher anywhere under src/ — confirmed independently by the verifier. direct: the content-hash-skip principle this depends on is already shipped and already load-bearing in a design decision: CHANGELOG.md:12, on removing push --scope formevents, states "The separate scope only skipped the web resource pass — and that pass writes nothing when dist/ is unchanged, so it bought no fewer writes."
Rationale
This is the highest-frequency command in the entire workflow — every UI code change round-trips through it, dozens of times a day, per developer. Every other idea in this set is experienced weekly at best. Most of the win is not the build: it is the CLI start, the auth-profile guard, and the enumeration running once instead of a hundred times.
Not already present
push --scope webresources --no-build is the fastest path available today and is still a full process start with a full auth guard per cycle. --dry-run is single-shot. Nothing loops.
Prior art overlap
None. The inner loop's latency appears in no prior ideation doc; the 2026-05-15 sync work addressed guards and dry-run, which is orthogonal.
Downsides
A genuine architectural conflict, not a hypothetical one. A documented pattern ties OrphanCleanupService's mutable-state safety explicitly to Flowline being single-command-per-process, and states that Flowline "cannot be safely server-ified or run simultaneous deployments." A long-lived watch process is the first thing to press on that invariant, so the design has to be built around it — most plausibly by keeping the watcher a thin loop that still isolates each push, rather than by holding engine state across cycles.
6
Act on declared deletions with a dependency-ordered deleter
Axis 4 · Component coverage Confidence 70% Complexity High
Description
The acting half of the deletion story. Idea 4 supplies the intent — deletions recorded by git itself in the commit that removed the file, reviewed in the pull request that carries it, and bounded by the target's stamped commit. Note the dependency this creates: consuming declared intent requires idea 4's authoritative stamp, written into the target by deploy. The version-and-tag pointer is good enough to report and not good enough to delete. This is what consumes them: one deleter that asks Dataverse for the dependency graph, orders topologically, and deletes, replacing the per-family handler zoo. Data-bearing types stay guarded regardless of declared intent.
Basis
external: tombstones in Cassandra, Dynamo and CRDTs exist because of exactly the constraint ALM-strategy.md §9 names as cost #1 — in an additive store, absence is ambiguous, and every such system resolves it by replicating the deletion as a positive record. Idea 4's refinement is that Flowline does not have to build that record — git's history of Solution/src/ already is one — so what this idea consumes is a git range, not an artifact. direct: Flowline's report-only tier is that ambiguity made visible: the workflow, bot, connection-reference, role and entity-family handlers all detect and report but never delete, graded in the changelog as "reported for you to remove by hand." They are report-only because inference is not trustworthy enough to authorise destruction — which is precisely what a declaration removes. direct: a grep confirms no RetrieveDependencies* call anywhere in src/; the two-phase ordering is hand-derived, and hand-deriving it produced a real bug in v0.14 (orphan assembly deletion blocked by step dependencies).
Rationale
This attacks the model's first documented cost at the root rather than the symptom, and it is the only route in the set that could shrink the manual-removal tier without Flowline getting better at guessing. It is also the rarer kind of change: it deletes code, replacing a hand-maintained ordering with the platform's own answer to the same question. Its scope shrank once idea 4 absorbed the intent-capture half — what remains is the machinery, and the machinery is where the risk actually lives.
Not already present
--force delete-orphans lowers the bar on an inference; it does not supply intent, and it does not change how the ordering is derived. Adding a component type to cleanup today means adding a handler.
Prior art overlap
The 2026-06-07 deploy doc proposed --prune and the 2026-06-10 orphan work documented the two-phase pipeline — both refine inference. This replaces the ordering derivation and acts on declared intent instead.
Downsides
Replacing a shipped, bug-hardened subsystem is the kind of rewrite that earns scrutiny before it earns a branch, and it is the reason this ranks below the record that feeds it. The tier structure must survive the change: data-bearing types (tables, columns, roles) stay guarded regardless of declared intent, because losing rows is categorically unlike unregistering a plugin step. And it inherits idea 4's scope limit — plugin types and steps never appear in solution XML, so those still arrive by inference rather than declaration.
7
Resolve auth before any Dataverse write
Axis 3 · Environment lifecycle Confidence 90% Complexity Low
Description
provision and init can create real Dataverse objects — an environment, a publisher, a solution — and only then discover the PAC auth profile is missing or ambiguous, because profile resolution is switch-only and never offers to create one. Move validation ahead of the first write, and offer to create the profile inline when none matches.
Basis
direct: CreateEnvironmentResolver.cs:81 — the resolver is documented in-code as "switch-only," erroring by naming pac auth create and never creating a profile or launching a login. direct: InitCommand.cs:202 is the consequence, told to the user after a failed Dataverse write: "clean up manually, or retry", naming the publisher ID, solution ID and environment. Both confirmed verbatim by an independent verifier.
Rationale
Six commands share one resolution path, so this is a root-cause fix in the repo's own idiom — a smaller diff than improving six error messages, and it eliminates the entire half-created-environment support class rather than documenting it. It is also the cheapest item in the set after idea 4.
Not already present
--auto-select-auth-profile disambiguates among existing profiles for unattended runs. It does not create a missing one, and it does nothing to move the failure point earlier. status detects mismatch and ambiguity, but only at check time — after provision or clone may already have written.
Prior art overlap
None. Auth-profile creation and its sequencing relative to writes appear in no prior ideation doc.
Downsides
An interactive profile-creation prompt is exactly wrong in CI, where there is no TTY — so the fallback behaviour needs deciding alongside the feature, not after it. The ordering change also touches a cross-cutting precondition used by every write path, which is a wider blast radius than the size of the fix suggests.
