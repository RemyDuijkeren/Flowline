Grounding Context

Codebase Context

Past learnings

  • The review used two rules for the PAC boundary without writing either: "PAC has this one" (G1, G2) and "the wrapper adds what PAC lacks" (G4, G5). Neither STRATEGY.md nor the cli-for-agents skill states a boundary rule (grep, 2026-10-31).
  • STRATEGY.md:68-71 owns type generation: it "removes the last reason to keep spkl installed". STRATEGY.md:31 keeps push and generate usable without a project.
  • sln add exists because dotnet sln add refuses a .cdsproj and exits 0 (SlnAddCommand.cs:19, dotnet/sdk#47638).

External context

  • PACX (Greg.Xrm.Command) is active (1.2026.10.257, 19 Oct 2026). It is a Dataverse metadata toolkit, not Git ALM. It overlaps on solution create, plugin push, plugin step enable|disable, webresources push|init, workflow activate|deactivate, forms, view. pacx settings is org settings, not deployment settings.
  • PAC overlaps on solution clone|sync|export|unpack|pack|import|create-settings, plugin init|push, modelbuilder build, admin copy. PAC's own option casing is inconsistent (--outputDirectory next to --settings-file).
  • No surveyed tool combines a Git clone, push, pull and deploy loop with DEV branched from PROD. That loop is the part only Flowline has.
  • clig.dev: same flag name for the same thing across subcommands; prefer flags over positionals; -o/--output for output.

1. Write the boundary rule down and run every command through it

Axis DConfidence 80%Complexity LowImplemented

Implemented 2026-10-31 in the commit "docs(strategy): state the PAC boundary rule and check every command against it": the rule and the per-command table are in STRATEGY.md under "Compose PAC, don't mirror it", and the cli-for-agents review checklist links to it.

Description

Add a boundary section to STRATEGY.md with one admission test. A Flowline command earns its place when it composes PAC or dotnet primitives into the Git delivery loop, or adds a guard or state those tools lack. A one-to-one pass-through of a single pac or pacx verb is refused, and the help points at that verb instead. Link the test from the cli-for-agents checklist so new commands meet it before review.

Running today's surface through it answers your second question. Every command passes, and the reason each one passes is the thing to write down:

Basis
reasoned: G1 and G2 were rejected because "PAC has this one", and G4 was deferred because "the wrapper adds what PAC lacks" (review). Neither rule is written anywhere: no boundary text in STRATEGY.md or .claude/skills/cli-for-agents/SKILL.md (grep). direct: the per-command gaps cite SlnAddCommand.cs:19, ProvisionCommand.cs:152 and SettingsComponentCommands.cs:391-438, all read during verification. external: PACX wiki and PAC reference for the overlaps.
Rationale
The honest answer to "what should move to PACX" is: nothing today. Without a written rule, though, the question comes back each time PAC or PACX adds a verb. With the rule and the ledger, each recurrence takes a minute. The sln add row is the only one with an expiry date.
Downsides
A doc, not a code change, so it only helps if the review checklist points at it. The PACX overlap was checked against its wiki, not its source; whether PACX binds connection references or sets environment variable values is unverified.

2. One spelling for the solution name: --solution-name

Axis AConfidence 70%Complexity Medium
Description
Outside a project, push and generate take the solution as an optional positional [solution]. The settings commands take the same thing as --solution-name. Inside a project, push and generate accept the positional and check it against .flowline. Settings refuses the flag outright. Use the settings shape on push and generate: --solution-name, accepted only without a project. The old positional then fails as an unexpected argument. Keep a positional only on clone and init, where it names the thing being cloned or created.
Basis
direct: push validates a passed solution against config (PushCommand.cs:97), and generate does the same (GenerateCommand.cs:122). Settings: "--solution-name only applies outside a Flowline project. Inside one the solution comes from the project …" (SettingsSupport.cs:77). C1 says optional input is a flag, so the settings shape is the one that already follows the rule.
Rationale
This is the most likely guessed-wrong argument for an agent moving between commands, and the only one that differs in behaviour as well as spelling. It also leaves room for a later rule: no command accepts a solution name inside a project.
Downsides
Breaking for stand-alone users: push ContosoCustomizations is a registered help example (Program.cs:436), and the README and wiki use the positional. Stand-alone mode is the progressive-adoption path (STRATEGY.md:31), so the break lands on new users. A one-release error that names the new flag softens it.

3. Make the written contract match the code

Axis EConfidence 90%Complexity Low
Description

One pass that brings the rules agents read in line with the shipped surface:

  • cli-for-agents SKILL.md:82 ("--dry-run on anything that writes") and checklist line 201 contradict C6. Scope the rule to what C6 kept: Dataverse writes that git can't undo.
  • STRATEGY.md still says sync (lines 24, 33, 54, 60) and lists init as post-v1 (line 133).
  • --client-id and --client-secret help says "(XrmContext/XrmContext3 only)" (GenerateCommand.cs:55,59). The code also promotes the profile to a service principal for other generators (GenerateCommand.cs:196-203).
  • diff --force x, scaffold --force x and sln add --force x fail with "Use one of: ." and an empty list (FlowlineSettings.cs:26, empty default at FlowlineCommand.cs:77). status has a hand-written message for the same case. Give the empty-list case the status message.
Basis
direct: every line cited above was read during verification. The C6 decision text: "both are reversible with git … is the dry run" (review, C6).
Rationale
Agents treat the skill checklist as policy. An unscoped dry-run rule will get C6 reopened by accident at the next review, and STRATEGY.md sends readers looking for a command that is reserved and unregistered.
Downsides
No single item would justify a meeting. It belongs in the list because idea 4 can only enforce rules that are written correctly.

4. One test that enforces the surface rules over the real command tree

Axis BConfidence 75%Complexity Medium
Description
Walk the registered command tree from the same configuration the CLI uses and assert the decided rules instead of remembering them:
  • Every option has a description.
  • A flag name (--dry-run, --exit-code, --path, --solution-name, --settings-file) has one type and one direction everywhere.
  • --skip- appears only on read-only gates.
  • Every --force vocabulary is non-empty or the command rejects --force clearly.
  • Aliases come from an allow-list, so new stays allowed under P11.
Known deviations go in a named allow-list with their decision ID, so the list only shrinks. Pair it with a short vocabulary table in the cli-for-agents skill: one row per concept (environment, solution, input artifact, output file, preview, exit-on-findings), the canonical spelling, and the allowed exceptions.
Basis
direct: the parsing tests already build the real app: "every app here is built through CliConfiguration.Configure, the same method Program.cs calls" (tests/Flowline.Tests/ProgramParsingTests.cs:8-9). Those tests guard one old spelling each (for example the --pluginFile case); nothing guards a new one. The checklist rules exist only as prose (SKILL.md:199-207).
Rationale
The settings branch introduced three new inconsistencies within weeks of a full surface review. A review fixes the surface once; a test keeps it fixed. It would have caught the --settings-file direction split and the empty force list.
Downsides
Reading the command model from Spectre needs reflection over settings types, which costs test upkeep. Some rules (a flag's direction) need a hand-kept table and can't be inferred.

5. Rename settings push/pull before the verbs set

Axis CConfidence 55%Complexity Medium
Description
Root push registers code assets into DEV and root pull exports the solution from DEV. settings push applies a settings file to any environment and settings pull writes one from any environment. Same verbs, different objects, different environment rules. Rename the settings pair after what it does, the way KTD25 already named toggle and set: settings apply and settings capture. Each verb then appears once in the tree with one meaning. --settings-file is still an input on one and an output on the other, but "apply a file" and "capture to a file" make that direction obvious.
Basis
direct: "Two component operations, named for what they do rather than for what they address (KTD25)" (Program.cs:531-532). P10 deferred the settings grammar; it shipped afterwards (commit d0cddbe), so this does not reopen a decision.
Rationale
An agent that learns pull as "DEV only, clean tree" carries that to settings pull test and gets it wrong. The settings branch is still pre-1.0 and has had one rename already, so a second costs little now and more later.
Downsides
Breaking, and the second rename of this branch in two months. Push/pull pairs well with git and PAC habits; apply/capture is clearer but less familiar. Leaving the names and adding one line to the branch description is the cheap fallback.

6. Retire the xrmcontext3 generator backend

Axis DConfidence 45%Complexity Low
Description
generate carries four backends. xrmcontext3 can't run unattended on a UNIVERSAL profile, and its own error message sends users to XrmContext v4. Deprecate it with a warning for one release, then remove it. Keep generate itself and the client credential flags (C10); this only shrinks the backends Flowline has to test and support.
Basis
direct: "xrmcontext3 uses ADAL browser OAuth for UNIVERSAL profiles …" and "Alternatively, upgrade to XrmContext v4 using --generator xrmcontext" (GenerateCommand.cs:368-372).
Rationale
It is the one backend that breaks the unattended contract AGENTS.md says most runs depend on, and the code already recommends the replacement.
Downsides
No usage data, so the cost to anyone still on v3 output is unknown. The saving is real but small; this may not be worth a meeting on its own.
